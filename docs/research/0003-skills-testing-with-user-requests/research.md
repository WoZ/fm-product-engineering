# Автоматическое тестирование exploration-input-clarification

Дата исследования: 6 ноября 2026 года. Основание: [задача](input.md) и уточнения пользователя: переносимая методика с примером для Codex, отчет на русском. Это исследование и предложение тестового контура, а не реализованный инструмент или новая спецификация скилла. Все диалоги и результаты ниже синтетические.

## 1. Рекомендация и предмет проверки

Рекомендую **вариант 5: гибридный контур**, начиная с небольшого набора ветвящихся сценариев, проверок действий и файлов, а также отдельной смысловой оценки. LLM-симулятор пользователя стоит добавить позднее для поиска необычных диалогов. Для основной регрессии достаточно заранее определенного намерения пользователя и разрешенных ответов на вопросы.

Главная единица проверки — **траектория диалога вместе с действиями и артефактом**. Правильный финальный файл не оправдывает запись до подтверждения, а красивый ответ не доказывает существование файла. Оценивать только последнее сообщение недостаточно.

Объект исследования — текущий [SKILL.md](../../../plugins/fm-research-and-analysis/skills/exploration-input-clarification/SKILL.md), разделы 1–5. На момент чтения HEAD: `f7aca9c`; SHA-256 файла: `4054ee56dc839a331f8198f625e969681c201846806553478f86155a3ff4d0af`. Хеш фиксирует именно исследованный текст; один commit ID не учитывает незакоммиченные изменения.

В репозитории отсутствует настроенный тестовый контур. [Корневой README](../../../README.md#current-state) и [README плагина](../../../plugins/fm-research-and-analysis/README.md#package-and-verification-status) сообщают о статической проверке без подтвержденного выполнения workflow. Этот отчет не меняет такой статус.

### Проверяемый контракт

| Участок | Что наблюдать | Что считается нарушением |
|---|---|---|
| Чтение input | Использованы переданные материалы; недоступность сообщена | Выдуманное содержание недоступного файла; самостоятельное исследование темы |
| Clarification | Вопросы разрешают существенную неоднозначность намерения | Пропуск блокирующей неоднозначности; вопросы о деталях, допустимых для brief или исследования |
| Readiness | Намерение, предмет и ожидаемый результат различимы | Широкий пересказ скрывает несколько разных задач |
| Restatement | Границы и предпочтения сохранены; запрошено подтверждение | Предпочтение стало обязательным требованием; предложенное допущение стало фактом |
| Correction | Исправление учтено, новая формулировка предъявлена и подтверждена | Старое подтверждение использовано для существенно измененного содержания |
| Saving | После подтверждения сохранен доступный результат нужного содержания | Преждевременная запись результата; перезапись без разрешения; ложное сообщение об успехе |
| Завершение | READY, подтверждение текущего содержания и сохранение выполнены вместе | READY или конец одного вызова объявлены завершением всего workflow |
| Вне области | Для понятного запроса без исследования объяснена неприменимость | Начат другой workflow; заранее выбранное решение ошибочно признано достаточным основанием для отказа |

Статусы `READY`, `CLARIFICATION REQUIRED`, `NOT AN EXPLORATION` определены скиллом. Он не задает машинную сериализацию каждого хода. Проверки не должны требовать точного расположения этих слов, определенных заголовков, числа вопросов или показа десяти внутренних критериев анализа. Не нужно собирать внутренние рассуждения модели: нужны сообщения, действия и результаты.

Для тестового драйвера полезны производные метки «ждем уточнения», «ждем подтверждения», «сохранение не выполнено», «завершено». Это интерпретации наблюдателя, а не дополнительные статусы текущего скилла. Их нельзя приписывать агенту без указания основания.

## 2. Основания и возможности хоста

Официальная статья [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills) предлагает фиксировать выполнение, проверять конкретные действия и добавлять оценку по рубрике для качественных требований. Ее пример посвящен созданию приложения. Применение этой схемы к многошаговому уточнению — вывод данного исследования; готовый тестер нашего диалога статья не предоставляет.

В [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) описаны ограничения LLM-оценивания, включая предпочтение длинных ответов и влияние порядка при сравнении. Поэтому автоматическую смысловую оценку следует сверять с разметкой автора на примерах правильного и ошибочного поведения. Хорошее согласие нельзя предполагать заранее.

Для конкретного адаптера Codex документированы следующие средства:

| Возможность | Применение в тестах | Граница гарантии |
|---|---|---|
| `codex exec --json` | Получить JSONL-события выполнения | События хоста не являются фазами нашего скилла |
| `codex exec resume <SESSION_ID>` | Передать следующий ответ в прежнюю сессию | Само продолжение не выбирает корректную ветку сценария |
| `-o` | Сохранить последнее сообщение агента | Это может быть вопрос, а не финальный clarified input |
| `--output-schema` | Структурировать отдельный отчет оценщика | Валидная структура не доказывает правильность оценки |
| `--sandbox workspace-write` | Разрешить сохранение в тестовом workspace | Требуется проверять фактический доступ и ограничения среды |

Источники: [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode), [CLI reference](https://learn.chatgpt.com/docs/cli/reference). Локально прочитаны `codex --version`, `codex exec --help` и `codex exec resume --help`: установлен `codex-cli 0.167.0`, перечисленные интерфейсы присутствуют. Это проверка справки, без вызова модели, проверки аутентификации или поведения диалога.

**Расхождение источников:** разделы 3 и 5 статьи о тестировании используют `--full-auto`; актуальная страница Non-interactive mode сообщает, что флаг больше не поддерживается. В новых примерах ниже выбран `--sandbox workspace-write`. Команды из статьи нельзя переносить без сверки с целевой версией CLI.

## 3. Пять подходов

Подходы различаются способом проведения теста, а не расширением отчета. Для каждого отдельно указано, что сохранять. Их можно сочетать, но итоговую рекомендацию следует оценивать с учетом стоимости всех компонентов.

### Вариант 1. Изолированные проверки фаз на подготовленной истории

Передать агенту input и историю, заканчивающуюся перед интересующим действием. Например: пользователь исправил формулировку после прежнего подтверждения; проверить, запросит ли агент подтверждение обновленного понимания.

**Фиксация:** версия fixture, подготовленная история, единственный новый ответ, действия и результаты проверок. Для проверки сохранения добавить снимки файлов до и после.

**Плюсы:** легко локализовать дефект; короткие запуски; удобно проверять редкие ошибки и исправления.

**Минусы:** искусственная история не показывает, придет ли агент к этому состоянию самостоятельно; контекст может отличаться от нативной сессии. Если хост не принимает историю с исходными ролями, ее передача как текста — более слабая имитация, что нужно указать в отчете.

**Риски:** fixture незаметно содержит ответ или подсказывает следующий шаг; тест проходит на вымышленной истории, хотя сквозной workflow сломан.

**Пример:** история содержит restatement A, подтверждение A и последующее «исправление: мне нужны выбранные авторы». Успех: агент пересматривает затронутые вопросы и предъявляет B на подтверждение; запись B на основании согласия с A — ошибка.

**Когда выбирать:** как быстрый диагностический слой рядом со сквозными тестами.

### Вариант 2. Линейные сквозные сценарии

Запустить скилл с начальным input и передавать заранее записанные реплики по очереди. Между ними проверять, что предыдущий ход соответствует ожидаемой стадии.

**Фиксация:** весь фактический диалог, исходный сценарий, события каждого вызова, контрольные снимки и итоговый артефакт. Ожидаемый диалог хранится отдельно от полученного.

**Плюсы:** простая автоматизация; фиксированный пользовательский ввод; хорошо подходит для понятного запроса и стандартного цикла подтверждения.

**Минусы:** корректный агент может объединить вопросы или задать их в другом порядке. Тогда очередная реплика из сценария перестает отвечать на реальный вопрос.

**Риски:** тест продолжает отправлять ответы после рассогласования; безусловное «да» подтверждает ошибочную формулировку; буквальное сравнение текста ошибочно отклоняет корректную перефразировку.

**Пример:** полный понятный input → restatement → проверка смысла → «да, верно» → сохранение. Если первый ход содержит блокирующий вопрос, драйвер останавливает этот линейный сценарий и фиксирует причину, а не отправляет подтверждение наугад.

**Когда выбирать:** для небольшого устойчивого набора простых сквозных путей.

### Вариант 3. Ветвящиеся сценарии с моделью состояния

У сценария есть неизменяемое намерение пользователя, разрешенные ответы и ожидаемые свойства переходов. Драйвер выбирает ответ по смыслу фактического вопроса, допускает группировку вопросов и следит за историей подтверждений.

**Фиксация:** все данные варианта 2, выбранные ветки, версии правил распознавания, основания классификации и связь подтверждения с конкретным restatement.

**Плюсы:** проверяет реальный многошаговый путь; устойчивее к вариативности разговора; позволяет точно задать отказ, исправление и повторное подтверждение.

**Минусы:** сценарии и распознаватель требуют сопровождения. Чистые регулярные выражения плохо различают близкие намерения; применение LLM для распознавания добавляет отдельную вероятность ошибки.

**Риски:** дефект драйвера становится ложной ошибкой скилла; слишком жесткие ветки запрещают допустимый порядок вопросов; тестер незаметно сообщает пользователю неизвестные факты.

**Пример:** на вопрос об авторах ответить «только выбранные мной»; на вопрос о частоте сообщить «оставим для исследования». При совмещенном вопросе дать оба ответа. Подтверждать только формулировку, сохраняющую выбранных авторов. Неизвестный существенный вопрос — `INCONCLUSIVE` и ручной разбор ветки.

**Когда выбирать:** как основу регрессии фазового скилла, особенно для уже известных ошибок.

### Вариант 4. LLM-симулятор пользователя и отдельный оценщик

Одна модель выполняет скилл, вторая отвечает как пользователь по закрытой карточке намерения. После диалога отдельный вызов оценивает сообщения, действия и артефакт по рубрике.

**Фиксация:** карточка и инструкции симулятора, фактически раскрытые факты, все сообщения, модели и настройки обеих ролей, отчет оценщика с ссылками на доказательства. Карточка не попадает к проверяемому агенту.

**Плюсы:** разнообразные формулировки и неожиданные ветки; меньше ручного перечисления диалогов; полезно искать неизвестные дефекты.

**Минусы:** дополнительные модельные вызовы; сложнее воспроизвести ситуацию; нужно оценивать самого симулятора. Отдельная роль или модель не гарантирует независимость ошибок.

**Риски:** симулятор подстраивается под ошибку агента, изобретает предпочтения или слишком охотно подтверждает; оценщик предпочитает убедительный текст фактическим доказательствам. Текст артефакта также может содержать инструкции, которым оценщик не должен следовать.

**Пример:** симулятор знает, что интересуют выбранные авторы, но в первом сообщении говорит только о «постах людей по теме». Он раскрывает ограничение в ответ на соответствующий вопрос и отклоняет пересказ про всех авторов. Оценщик отдельно проверяет, не нарушил ли симулятор эту роль.

**Когда выбирать:** для исследовательских прогонов и расширения покрытия; первоначально результаты требуют разбора автором.

### Вариант 5. Гибридный контур — рекомендуется

Основные пути задаются вариантом 3, короткие проверки фаз берутся из варианта 1. Действия, порядок и доступность файлов проверяются программно; смысл вопросов и restatement — по рубрике. Вариант 4 используется отдельно для поиска новых сценариев, которые после проверки автором превращаются в устойчивую регрессию.

**Фиксация:** единый пакет доказательств и отдельные результаты программных и смысловых проверок. Сводка не скрывает ошибок за средним баллом; неопределенные оценки видны отдельно.

**Плюсы:** проверяемые действия не зависят от мнения оценщика; смысл не сводится к совпадению слов; можно начать с малого и добавлять сложность по подтвержденной необходимости.

**Минусы:** больше компонентов, чем у линейного сценария; нужны калибровка оценщика и разбор спорных случаев.

**Риски:** сложность обвязки начинает превосходить сложность скилла; настройки тестера меняют измеряемое поведение. Снижение риска: одинаковая обвязка для сравниваемых версий и явное разделение ошибок хоста, драйвера и скилла.

**Пример:** программа устанавливает, что файл появился после u3; оценщик проверяет, что u3 подтверждает именно a2 и что a2 сохраняет намерение пользователя; содержание файла сравнивается с подтвержденным смыслом. Одного существования файла для `PASS` недостаточно.

### Сравнение

Оценки качественные, по устройству подходов; измерений стоимости и надежности здесь не проводилось.

| Вариант | Покрытие реального диалога | Повторяемость пользовательского ввода | Сопровождение | Основная слабость |
|---|---|---|---|---|
| 1. Фазы | Локальное | Высокая | Низкое–среднее | Искусственная история |
| 2. Линейный | Полное для одной траектории | Высокая | Низкое | Рассогласование реплик |
| 3. Ветвящийся | Полное для заданных веток | Высокая в пределах правил | Среднее | Ошибки распознавания веток |
| 4. Симулятор | Широкое, непредсказуемое | Ограниченная | Среднее–высокое | Ошибки симулятора и оценщика |
| 5. Гибрид | Целевое плюс поисковые прогоны | Высокая для регрессии | Среднее при постепенном внедрении | Сложность обвязки |

Даже фиксированные реплики не делают ответы модели детерминированными. «Повторяемость» здесь означает контроль входных условий и сохранение полного фактического выполнения.

## 4. Минимальный рекомендуемый контур и хранение

### Ответственность компонентов

1. **Сценарий** определяет исходный input, скрытое намерение, разрешенные ответы, проверяемые условия и ожидаемый вид окончания. Скиллу видны только доставленные пользовательские сообщения и явно предоставленные материалы.
2. **Драйвер** начинает новую сессию для каждого независимого запуска, передает по одному ответу, выбирает ветку и ограничивает продолжительность. Для начала предлагается максимум 12 ответов агента и 180 секунд на ход; превышение лимита само по себе не доказывает дефект скилла. Это настраиваемые пределы тестера, не требования workflow.
3. **Адаптер хоста** вызывает агента, сохраняет наблюдаемые события и сообщения, фиксирует ошибки и идентификаторы. Неподдерживаемый интерфейс вопросов не считается ответом пользователя: требуется другой адаптер либо явный незавершенный тест.
4. **Проверки** сопоставляют хронологию, файловые снимки и содержание. Оценщик получает рубрику, историю, скрытое намерение и доказательства только на этапе оценки; проверяемому агенту рубрика не подсказывает решение.
5. **Отчет** сохраняет результаты каждого условия и ссылки на доказательства, позволяя автору проверить вердикт.

Закрытые fixtures и отчеты следует хранить вне доступного агенту workspace. Нельзя класть скрытую карточку в соседний файл с расчетом, что агент ее не прочитает. Для реальной изоляции нужны возможности хоста; текстовый запрет их не заменяет. В workspace копируется точная версия скилла и только необходимые публичные материалы, без symlink, ведущего в исходный checkout. Контекстные инструкции и доступные инструменты фиксируются отдельно: запуск в минимальной среде и запуск с репозиторными инструкциями проверяют разные конфигурации.

Перед каждым ходом и после него сохраняются состояние целевого файла и наблюдаемые операции записи. Проверяется содержание, а не только наличие пути. Для ошибки записи нужен воспроизводимый отказ хоста или инструментальная имитация с указанным уровнем теста; случайный недоступный путь не доказывает, что проверена нужная ветка. Одних снимков между ходами недостаточно, чтобы исключить кратковременную запись с последующим удалением. Если трасса таких операций недоступна, проверка отсутствия преждевременной записи помечается неполной.

### Пакет результатов

Предлагаемая структура, в репозитории не создана:

```text
<run-id>/
├── run.json
├── transcript.jsonl
├── host-events.jsonl
├── checks.json
├── report.md
└── artifacts/
    ├── before.md
    └── after.md
```

`run.json` содержит идентификаторы сценария и повтора, дату, хеши скилла и fixture, версии CLI/адаптера/проверок, модель и настройки, идентификатор сессии, эффективные ограничения среды и лимиты. Версии симулятора и оценщика записываются отдельно. Недоступные сведения отмечаются как неизвестные. Секреты аутентификации в пакет не входят.

`transcript.jsonl` — нормализованный журнал доставленных сообщений с ID и порядком. `host-events.jsonl` сохраняет доступную трассу хоста, не объявляя ее универсальным протоколом. Длинные технические трассы хранятся отдельно от читаемой сводки; внутренние рассуждения не являются данными для оценки. Если сырой поток хоста включает такие элементы, набор сохраняемых типов должен быть явно ограничен и описан адаптером.

`checks.json` содержит для каждого условия тип проверки, вердикт, причину и ссылки на сообщения/действия/снимки. Markdown генерируется из этих результатов; независимое редактирование двух наборов оценок создает риск рассинхронизации. JSONL выбран для последовательности сообщений, JSON — для итогового результата, Markdown — для просмотра автором. Эти форматы сами не обеспечивают правильность или полноту доказательств.

Предлагаемые вердикты тестера:

| Вердикт | Значение |
|---|---|
| `PASS` | Все обязательные проверки пройдены, доказательства достаточны |
| `FAIL` | Есть подтвержденное нарушение контракта скилла |
| `ERROR` | Сбой запуска, адаптера, окружения или невалидное поведение симулятора мешает оценке |
| `INCONCLUSIVE` | Запуск состоялся, но данных или надежности оценки недостаточно |

При подтвержденном нарушении итог остается `FAIL`, даже если другие проверки неполны. Иначе `ERROR` и `INCONCLUSIVE` не превращаются в успех. Успешный тест отказа или ожидания подтверждения получает `PASS`, хотя сам workflow закономерно не завершен. Правильный отказ вне области также может быть `PASS`.

### Смысловая рубрика

Для каждого пункта оценщик выбирает `PASS`, `FAIL` или `INCONCLUSIVE` и указывает сообщения, на которых основан вывод:

- Различены ли существенно разные намерения до READY?
- Нужен ли каждый заданный вопрос для понимания input на этой фазе?
- Сохранены ли предмет, ожидаемый результат, границы, предпочтения и статус гипотез?
- Подтверждена ли актуальная формулировка, без приписывания согласия на отдельно отмеченные предложения?
- Сохранил ли документ существенные уточнения и корректно ли отнесены открытые вопросы к brief или исследованию?

Краткая причина с цитатой или ID сообщения полезнее свободного «общего впечатления». Трасса и артефакт считаются данными: инструкции внутри них не меняют рубрику. Оценщика следует калибровать на размеченных автором примерах, включая правильные перефразировки, лишние вопросы и скрытый пропуск неоднозначности; фиксировать ложные пропуски и ложные тревоги. Программный факт записи нельзя отменять положительной смысловой оценкой.

## 5. Примеры сценария, диалога и отчета

### Закрытая карточка сценария

Ниже иллюстративный JSON для драйвера, не готовая схема и не input скиллу. Английские реплики позволяют использовать тот же пример без перевода технических данных; реальный набор должен включать и русский ввод.

```json
{
  "case_id": "selected-authors",
  "initial_message": "I want to explore how to receive people's LinkedIn posts about infrastructure.",
  "user_intent": "Follow posts from authors I select; do not discover arbitrary authors.",
  "answers": {
    "author_scope": "Only authors I select.",
    "delivery_frequency": "Leave delivery frequency open for the research."
  },
  "destination": "clarified-input.md",
  "mandatory_checks": [
    "clarify-author-scope",
    "preserve-selected-authors",
    "confirm-current-restatement",
    "save-after-confirmation",
    "stop-before-brief"
  ],
  "expected_workflow_outcome": "completed",
  "max_agent_turns": 12
}
```

Начальное сообщение само по себе неоднозначно. Скрытое намерение не считается уже сообщенным. Не нужно требовать вопрос именно со словом «авторы»: смысловое уточнение того же различия допустимо. Неизвестные предпочтения не выдумываются; при новом блокирующем вопросе, которого карточка не покрывает, драйвер оставляет случай для разбора.

### Синтетическая успешная траектория

| ID | Кто | Содержание или действие | Проверка |
|---|---|---|---|
| u1 | Пользователь | Хочет получать посты людей про инфраструктуру | Передан только начальный input |
| a1 | Агент | Уточняет: выбранные авторы или поиск любых авторов? | Различена блокирующая неоднозначность |
| u2 | Пользователь | Только выбранные авторы; сохранить в clarified-input.md | Доставлены ответ и путь |
| a2 | Агент | Пересказывает задачу про выбранных авторов, просит подтвердить | Нет добавленного поиска произвольных авторов; файла еще нет |
| u3 | Пользователь | Да, это верно | Подтверждение относится к a2 |
| t1 | Инструмент | Сохраняет clarified-input.md | Успешная запись после u3 |
| a3 | Агент | Сообщает путь и завершает фазу | Файл читается; brief не начат |

Частота доставки может остаться открытой, если она не мешает понять подтвержденное намерение. Если она существенна для сохраненного результата, ее нужно обозначить как открытый вопрос с объяснением. Тест не должен навязывать отдельный вопрос о ней во всех случаях.

Производный пример нормализованного журнала, не формат событий Codex:

```jsonl
{"sequence":1,"message_id":"u1","role":"user","text":"I want to explore how to receive people's LinkedIn posts about infrastructure."}
{"sequence":2,"message_id":"a1","role":"assistant","text":"Do you mean authors you select, or discovering anyone who posts about infrastructure?"}
{"sequence":3,"message_id":"u2","role":"user","text":"Only authors I select. Save the clarified input to clarified-input.md."}
```

### Пример записи результата

Ниже сокращенный фрагмент `checks.json` для описанной успешной траектории. ID доказательств разрешаются внутри пакета конкретного запуска; пример не свидетельствует о реально выполненном тесте.

```json
{
  "run_id": "selected-authors-r1",
  "case_id": "selected-authors",
  "verdict": "PASS",
  "workflow_outcome": "completed",
  "checks": [
    {
      "id": "preserve-selected-authors",
      "kind": "semantic",
      "verdict": "PASS",
      "evidence": ["u2", "a2", "artifacts/after.md"],
      "reason": "The restatement and saved input restrict the subject to selected authors."
    },
    {
      "id": "save-after-confirmation",
      "kind": "action-order",
      "verdict": "PASS",
      "evidence": ["a2", "u3", "t1"],
      "reason": "The observed write follows confirmation of the current restatement."
    }
  ]
}
```

Читаемая сводка добавляет результат остальных обязательных проверок и ограничения наблюдаемости. В настоящем полном отчете пропущенная обязательная проверка исключает итоговый `PASS`.

**Пример неуспеха:** a2 говорит о поиске всех авторов по теме; драйвер отклоняет эту формулировку, а агент все равно сохраняет файл. Проверки сохранения намерения и подтверждения получают `FAIL` с ссылками на a2, отказ и запись. Наличие Markdown-файла не меняет вердикт.

**Пример корректной незавершенности:** после a2 пользователь отказывается подтверждать. Агент завершает ответ без заявления об успехе и без сохраненного результата. Тест ожидания/отказа получает `PASS`, workflow — `awaiting_confirmation`. Если драйвер просто не отправил следующий ход, проверяется только поведение до этой границы; нельзя утверждать, что испытана реакция агента на длительное молчание.

### Пример адаптера Codex

Это иллюстративная последовательность вызовов после подготовки изолированной среды, а не готовый runner. Пути принадлежат новому запуску; каталог отчета расположен вне workspace агента. В workspace подготовлена локальная копия скилла в `.agents/skills/exploration-input-clarification`, публичные материалы и никаких закрытых fixtures. Предполагаются установленный CLI, настроенная аутентификация и доступная модель. Обнаружение скилла необходимо проверить до оценивания поведения.

```bash
codex exec --ignore-user-config --sandbox workspace-write \
  --skip-git-repo-check --cd /tmp/skill-case-selected-authors \
  --json -o /tmp/skill-evidence-selected-authors/turn-1.txt \
  'Use $exploration-input-clarification. I want to explore how to receive people’s LinkedIn posts about infrastructure.' \
  > /tmp/skill-evidence-selected-authors/turn-1.jsonl
```

Драйвер читает события, получает `thread_id`, сохраняет stderr и код выхода отдельно. Затем проверяет вопрос и отсутствие преждевременной записи. Только после выбора соответствующей ветки передает ответ. В примере переменная `case_session_id` заранее присвоена драйвером из события начавшейся сессии:

```bash
codex exec resume --ignore-user-config --json \
  -o /tmp/skill-evidence-selected-authors/turn-2.txt \
  "$case_session_id" \
  'Only authors I select. Save the clarified input to clarified-input.md.' \
  > /tmp/skill-evidence-selected-authors/turn-2.jsonl
```

Подтверждение отправляется аналогичным вызовом только после проверки текущего restatement. В драйвере команды следует формировать массивом аргументов без shell-интерполяции пользовательского текста. Не использовать `--last`: другой тест может создать более новую сессию. Не использовать `--ephemeral` для цепочки, рассчитывающей на сохраненную сессию.

Права и рабочий каталог продолжения должны соответствовать началу сессии и проверяться адаптером; нельзя механически переносить все флаги начального `exec` после `resume`. `--ignore-user-config` исключает загрузку основного пользовательского config, но сам по себе не доказывает отсутствие других инструкций, skills или интеграций. Нужна контролируемая среда; эффективные настройки записываются в run.json. Переносимый протокол драйвера не должен зависеть от имен полей конкретной версии CLI.

`--output-schema` предлагается использовать в отдельном вызове оценщика. Принудительный JSON на каждом ходе проверяемого скилла меняет условия диалога и требует контракта, которого сейчас нет. Если агент запросит специальный интерактивный инструмент, недоступный в `exec`, это ограничение адаптера: нельзя подставлять фиктивный успех вместо пользовательского ответа.

## 6. Покрытие, внедрение и ограничения

### Начальная матрица сценариев

| Сценарий | Ожидаемое поведение |
|---|---|
| Полный понятный input | Без лишних вопросов перейти к restatement и подтверждению |
| Два разных намерения под одной общей формулировкой | Уточнить различие до READY |
| Выбор решения оставлен исследованию | Не требовать выбрать решение сейчас |
| Противоречащие обязательные ограничения | Уточнить; не назначать приоритет за пользователя |
| Исправление после restatement | Учесть исправление и получить подтверждение актуальной формулировки |
| Новая блокирующая неоднозначность после согласия | Вернуться к уточнению; согласие не устраняет пропущенный вопрос |
| Отказ отвечать на блокирующий вопрос | Перепроверить блокирующий характер, сохранить незавершенность при необходимости |
| Нет подтверждения / явный отказ | Не объявлять завершение и не сохранять финальный input |
| Только выполнение определенной задачи | Объяснить NOT AN EXPLORATION, не начинать другой workflow |
| Заранее выбранное решение, исследуются его риски | Не отклонять только из-за фиксированного решения |
| Недоступный входной файл | Сообщить ограничение, запросить необходимый input |
| Нет пути и соглашения хоста о сохранении | Запросить путь, когда сохранение необходимо |
| Целевой файл уже существует | Не перезаписывать без разрешения; исходное содержание сохранено |
| Ошибка записи | Выдать подготовленное содержание в чате, сообщить несохраненность и оставшийся шаг |
| Сохранение прошло | Проверить содержание, читаемость, путь и отсутствие перехода к brief/исследованию |
| Попытка самостоятельно исследовать тему | Зафиксировать выход за границы, различая загрузку явно переданного материала и поиск новых источников |

Для каждого случая нужны конкретные ввод, закрытая карточка и критерии приемки. Матрица — план покрытия, а не уже реализованные тесты. Запрет самостоятельного исследования оценивается по цели действия и доступным событиям; простой поиск слова `search` в логе ненадежен.

### Последовательность внедрения

1. Разметить автором ожидаемое поведение для начальной матрицы и несколько намеренно неправильных диалогов. Проверить, что сами проверки отклоняют запись до подтверждения, подмену намерения и ложное сохранение.
2. Реализовать драйвер ветвящихся сценариев и адаптер Codex, проверить обнаружение скилла и сквозной успешный путь. Хранить инструментарий разработки отдельно от дистрибутива, если он не нужен установленному плагину; точное размещение требует отдельной задачи реализации.
3. Добавить файловые/хронологические проверки, затем откалиброванный смысловой оценщик. Начать с трех повторов на сценарий для выявления нестабильности; это предложенный стартовый режим, не статистическая гарантия.
4. Сравнивать базовую и измененную версии на одинаковых сценариях, моделях и окружении. Публиковать результаты по условиям и сценариям, число `FAIL`, `ERROR`, `INCONCLUSIVE`, число повторов, длительность, доступные данные расхода и долю расхождений оценщика с автором. Не скрывать инфраструктурные ошибки исключением из общей сводки.
5. Добавлять LLM-симуляцию после устойчивого основного контура. Сохранять найденные диалоги для разбора; преобразование их в улучшения скилла относится к [отдельной задаче 0004](../0004-skill-test-cases-with-auto-improvement/input.md).

До проверки оценщика спорный результат требует разбора автора. Повторный запуск не стирает прежний провал: сохраняются все попытки. Нулевая температура, фиксированное имя модели или несколько успешных повторов не дают гарантии одинакового поведения в будущем. Порог автоматического допуска к релизу здесь не вводится.

### Согласованность и выполненная проверка

Проверены текущий SKILL.md, метаданные `allow_implicit_invocation: false`, корневые инструкции и README, README плагина, применимые conventions и [исследование 0001](../0001-exploration-input-clarification-outcome-format/research.md). Выполнены чтение первичных источников, проверка локальной справки CLI, статический разбор JSON/JSONL-примеров, проверка локальных ссылок, ограждений кода и пробелов нового документа. Модельные тесты, установка плагина, runner и JSON Schema не реализованы и не запускались.

Связанные расхождения и границы:

- Корневой [AGENTS.md](../../../AGENTS.md) и [Documentation, Rules](../../../repository-governance/conventions/documentation.md#rules) требуют American English. Русский язык отчета — прямое согласованное исключение пользователя для этой задачи; изменение общей политики не требуется.
- В [0001, раздел 4](../0001-exploration-input-clarification-outcome-format/research.md) предлагаются машинные состояния, редакции и контрольные точки. Эти предложения не внесены в текущий скилл. Требовать их наличия в текущих тестах означало бы проверять будущую спецификацию. Коррекция для тестового контура: выводить метки наблюдателя отдельно и ссылаться на доказательства. Переписывать историческое исследование не требуется.
- Расхождение внешней статьи и актуальной CLI-документации по `--full-auto` описано в разделе 2; примеры адаптированы к справке установленной версии. Локальные документы этим отчетом не синхронизируются с внешней статьей.
- Противоречий между предложенной методикой и текущими границами скилла/пакета при статическом просмотре не найдено. Этот вывод не устанавливает совместимость с другими хостами или полноту будущих проверок.

CLI при чтении справки вывел предупреждение о невозможности создать PATH aliases (`Operation not permitted`), но вернул код 0 и справку. Запуски модели не выполнялись, поэтому доступ к сервису, продолжение сессии, полный охват действий и обработка интерактивных вопросов остаются непроверенными. Статический разбор примеров подтверждает их синтаксис, а не работоспособность предложенного контура.
